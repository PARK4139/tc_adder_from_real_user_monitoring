- timestamp 병렬 로그는 RAM에 연동되는 내부 telemetry 기능으로 구현.

# steps
근거: 사용자 지시 2026-10-07: 수집결과 형태는 어떤 형태인가? timestamp 로 그 시기가 추정되는 형태도 로그형식으로 별도 병렬수집 되어야 한다. add issue.
범위 정정: 사용자 지시 2026-10-07: timestamp 병렬 로그는 MCP 아닌데? 내부 로그 수집 기능으로 관리하며 별도 MCP 도구 요구를 제거.
1. 기존 native/semantic 이벤트의 시각 필드와 수집 시점, 지연 및 관찰 공백을 확인하고 로그의 시각 의미를 문서화.
2. 기존 수집과 동시에 별도 activity.log에 사람이 읽을 수 있는 활동 기록을 지속 append. 종료 후 일괄 변환만 수행하는 방식은 병렬 수집으로 인정하지 않음.
3. 각 기록에 시간대 포함 ISO 8601 timestamp와 원본 epoch milliseconds, 관측 시각과 로그 기록 시각, session_id/run_id, 원본 stream/sequence, ui_id(미식별이면 명시), 변화 종류, 전후 내용 및 증거 경로 포함. 원본에 실제 발생 시각이 없으면 관측 시각으로 명시하고 발생 시각을 꾸며내지 않음.
4. 입력값·문구·색상 변화, 화면·모달·팝업 등장/소멸, 수집 시작/종료 및 observation_gap 기록. 늦게 도착한 이벤트도 원본 시각과 순번을 보존하며, 서로 다른 stream의 순번을 동일 순번 체계로 혼동하지 않음.
5. 별도 로그 writer를 RAM 시작·종료에 자동 연동하고, 기존 RAM/자동제어를 막지 않도록 운영. 쓰기 실패·누락·재시작 중복을 진단하고 로그 파일과 내부 상태 기록으로 확인.
6. 아래 단일 AC를 재현 가능한 관측 이벤트와 실제 RAM 세션으로 검증하고 증거 저장.
